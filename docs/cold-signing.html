Protocol 1.2 · Signing

Sign anywhere. Understand always.

Cold signing is a signing mode, not a separate product: every transaction in Ordex, from a marketplace purchase to a SafeOps batch, can be completed through a connected wallet, a hardware wallet, a PSBT file, or a QR, and every one of them is preceded by a manifest that says exactly what will move.

The manifest you review

Before any signing request, the flow builds an expected transaction manifest: the network, one line stating the purpose, every input with its exact value and script, whether you control it, its sighash type, and one line on why it is spent, every output with its exact script, value, role, expected assets, and one line on who receives it, and the fee with its permitted maximum. Human readable and machine verifiable at once, so both you and your tooling read the same truth.

What the digest covers

The manifest digest is SHA-256 over the sorted-key JSON of the network, the inputs (outpoint, value, script), the outputs (script, value), and the sighash policy. Presentation fields deliberately sit outside it. The unsigned transaction is the identity: if anything about what will move changes, the digest changes, and the flow presents it again instead of adapting quietly.

The nine refusals

After a signed result comes back, from any signer, it is compared against the manifest. Any difference is a refusal with a stable code, never an adaptation.

  1. The signed result was not produced from this manifest (MANIFEST_DIGEST_MISMATCH).
  2. The fee left its approved bound (FEE_OUT_OF_BOUNDS).
  3. An input was added, removed, or reordered (INPUT_SET_CHANGED, INPUT_REORDERED).
  4. An output was added, removed, or changed in script or value (OUTPUT_SET_CHANGED, SCRIPT_CHANGED, VALUE_CHANGED).
  5. A protected asset moved somewhere other than its expected output (PROTECTED_ASSET_MISPLACED).
  6. A required input of yours is still unsigned (REQUIRED_SIGNATURE_MISSING).
  7. A signature carries a sighash the manifest did not approve (SIGHASH_UNEXPECTED).
  8. A signature covers an input you do not control (SIGNATURE_ON_FOREIGN_INPUT).
  9. An unknown critical field appeared (UNKNOWN_CRITICAL_FIELDS).

The stepper shows the exact field and a human explanation, and keeps the stable code in the technical details.

The signing stepper

One flow carries every transaction: build, verify, export or connect signer, sign offline, import, verify the signed result, refresh chain state, run node preflight, take the explicit broadcast step, monitor settlement. Each step is resumable. The export carries the manifest digest, and the import step re-runs the full comparison before anything else happens.

Export paths: base64 copy and paste, a .psbt file, an animated QR through an established interoperable UR encoding, or a static QR when the payload fits safely. Hardware devices connect through their existing audited wallet-provider interfaces; no device key management lives in Ordex, and no key or recovery material ever passes through a gateway or SDK.

Watch-only, honestly

A watch-only profile is a standard output descriptor or xpub, stored locally by default. Nothing uploads an xpub or an address set without an explicit warning and an explicit action, and an optional synchronized profile is encrypted on your side under a key the server never sees. Watch-only surfaces show holdings, build plans, and export PSBTs; signing controls render as unavailable, labeled, never hidden.

No blind signing

If it was not in the manifest, you do not sign it.

A signer is never asked to sign a transaction whose manifest was not shown and verifiable. Hardware wallets that display their own interpretation must agree with the manifest on network, recipients, and amounts; a disagreement blocks the session and shows the disagreement.

Verify it yourself

  • Recompute the manifest digest from the unsigned transaction and compare it to what you reviewed.
  • Run verifier/offline-signing.js over any manifest and signed result pair.
  • Compare behavior against conformance/offline-signing-vectors.json, one case per refusal rule.
  • The SDK exposes the same checks; see the developer network.

The full contract is spec/cold-signing.md. Try it on a real plan through SafeOps or a swap session.
