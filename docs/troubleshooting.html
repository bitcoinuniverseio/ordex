Troubleshooting

Follow the evidence, not the assumption.

An Ordex state tells you which evidence layer needs attention. Start with gateway health, then the relevant input or asset claim, then relay and market visibility.

First check: identify the gateway

Inventory is only as current as the gateway that produced it. Confirm the selected gateway URL, its configured network, its Core reachability, and its ord reachability before diagnosing an individual order. A user may be looking at a self-hosted gateway while expecting a marketplace-operated one.

  1. Open the connection panel.Confirm whether the default marketplace gateway or a custom gateway is active.
  2. Read /health.Verify the expected network and dependent service configuration.
  3. Inspect the order state.Use the state as the next diagnostic branch; do not relabel a pending order as live.

Interpret the order state

StateLikely causeNext action
LIVECurrent configured checks succeeded.Still re-check immediately before settlement; this is time-bound evidence.
PENDING_NODENode unavailable, syncing, network mismatch, or input check pending.Repair Core access/sync, then refresh verification.
PENDING_ORDOrdinal index unavailable or claimed location unresolved.Repair/synchronize ord; verify the claimed outpoint.
MEMPOOL_CONFLICTEDAt least one input cannot be found as an unspent output.Treat the artifact as unavailable; obtain a current replacement from its publisher.
REJECTEDPSBT parse or safety profile did not satisfy the gateway.Review the rejection reason; do not work around it with an altered artifact.
WITHDRAWNThe local gateway removed the inventory projection.Do not infer a Bitcoin cancellation or global relay deletion.

Core and UTXO verification

Symptom: many unrelated orders show PENDING_NODE.

  • Confirm that the gateway is configured for the same network as the node.
  • Wait for the node to finish synchronization before treating local inventory as verified.
  • Keep Core authorization private to the gateway process; a browser connection to Core is not a repair.
  • When one order alone is conflicted, treat the input as unavailable rather than assuming a gateway fault.

Verification is not reservation.

gettxout observes availability at a moment in time. It cannot reserve an input, cancel another party's transaction, or turn a public PSBT ask into an exclusive offer.

ord and asset verification

Symptom: the UTXO is available but the order remains PENDING_ORD.

  • Confirm the ord endpoint is reachable from the gateway and is synchronized to the expected chain.
  • Compare the order's claimed inscription identifier and outpoint with the indexer's current location response.
  • Do not substitute collection metadata for a location check. The asset claim is verified at the outpoint level.
  • For a moved inscription, import or publish a new order artifact rather than mutating historical evidence.

Nostr relay publishing

Symptom: a NIP-07 signing prompt succeeded but the order is not discoverable.

  1. Check relay URLs.Use credential-free wss:// or ws:// URLs, one per line.
  2. Check acknowledgement.A signature is not delivery. Require an OK response for the matching event id from at least one relay.
  3. Check gateway import.Post the same signed event to the active Ordex gateway so it can independently verify and index it.
  4. Check filters.Protocol, token, source, side, state, and safety filters can hide a correctly indexed order.

Why an order appears on one market but not another

Ordex makes evidence portable; it does not force every market to show every record. Markets may use different relays, gateway refresh schedules, filter defaults, supported protocol templates, and local moderation policies. Compare the signed event, selected gateway, filters, and the gateway's local verification result before treating it as a protocol disagreement.

Safe recovery path

  • Record the gateway URL, order id, event id, and verification state.
  • Check the artifact against a synchronized gateway you trust.
  • If the input is unavailable, obtain a newly created artifact from the publisher.
  • If a relay did not acknowledge the event, publish a new signed event to a working relay rather than assuming silent delivery.
  • If details changed, create a new revision with an explicit lifecycle record; do not overwrite the prior artifact.
