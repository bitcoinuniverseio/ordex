Protocol 1.2 · Heritage

Old Counterparty assets. New settlement rules.

Named assets, numeric assets, subassets, and long names trade here as UTXO-attached assets with exact PSBT settlement: the attachment follows the sats, the buyer's payment and the seller's asset move in one transaction, and nobody ever forwards BTC to a legacy dispenser address.

Identity you can check

An asset's identity is the authoritative numeric Counterparty asset id together with its current ledger state. A ticker or a name alone is never an identity, and the gateway refuses records that try (ASSET_ID_REQUIRED). Every record names the asset name, the numeric id, divisibility, and the exact quantity as an atomic decimal string, so what you see is what the ledger says, not a rounded display value.

What attached means

A Counterparty attachment binds an exact quantity of one asset to one outpoint. That outpoint is spendable Bitcoin, but it is never cardinal: everything in Ordex that touches sats, from SafeOps consolidations to swap input selection, reads the same attachment registry and refuses to move an attached outpoint without preserving its complete declared inventory, including any co-traveling assets the record declares.

Undeclared neighbors are how assets get burned.

One outpoint can carry more than one attachment. The record declares every co-traveling asset, and every verification that spends the outpoint carries that declaration with it.

The rule that moves attachments

When an attached outpoint is spent, the attachment follows the input range: it lands in the first output whose accumulated value passes the input's range start, the same first-sat rule that decides inscription delivery everywhere else in Ordex. The verifier re-derives the destination from the spending transaction alone and refuses when the trace is impossible (SAT_FLOW_SHORTFALL) or lands somewhere other than the plan promised (DESTINATION_MISMATCH).

A listing is an Ordex ask over the attached outpoint: the seller's signed input commits the outpoint, the buyer's payment sits at the same index, and the sat-flow invariant guarantees the attachment arrives in the buyer's output. The purchase rules apply unchanged.

One authority, or none

The heritage market reads one self-hosted Counterparty Core deployment, the same node the rest of the ecosystem operates. A record may exist only while that authority reports ready, fresh, and on the intended network, and every record binds the block height, block hash, and ledger hash it was read at, so you can judge freshness yourself.

The market fails closed.

If the authority is unreachable, lagging, or on the wrong network, listing, buying, attach, and detach all stop with a stated reason. There is no public API fallback in production, ever.

Attach and detach

Attaching moves an address balance onto an outpoint you control; detaching returns it to an address balance. Both are composed for you and signed by you: the composition returns an unsigned PSBT, the exact XCP gas, the exact miner fee, the resulting outpoint, the consequences, and any unrelated assets that would also travel. You review all of it before your wallet opens, your wallet signs, and the expected Counterparty event is confirmed after confirmation. Reorgs reverse the marketplace state through explicit reversed events.

How trading works

Listings, purchases, swaps through the swap protocol, and seller withdrawal all work exactly as they do for ordinals, with the heritage adapter proving the attachment behind the scenes. Legacy dispensers and order history are displayed read-only with clear labeling. Nothing in the product sends BTC to a legacy dispenser address or encourages it.

What your wallet signs

The server never holds the asset, XCP, or BTC.

Attach, detach, listing, and purchase compositions are all unsigned PSBTs for your wallet. The gateway composes, verifies, and relays after your explicit broadcast action; it never contributes funds and never produces a signature.

Verify it yourself

  • Every attachment record carries the authority checkpoints it was read at; compare them against the readiness endpoint.
  • Run verifier/counterparty-asset.js over any record and any spending transaction to re-derive where the attachment lands.
  • Compare behavior against conformance/counterparty-asset-vectors.json, including the sat-flow and refusal cases.
  • The SDK exposes the same checks; see the developer network.
