Protocol 1.2 · Swaps

Two sides. One transaction. No escrow.

A swap is an asset-for-asset exchange that settles in exactly one Bitcoin transaction: either both sides move exactly as agreed, or nothing moves at all. There is no prefunded output, no escrow, no policy signer, and no server signature. This is not the 1.1 funded offer system and does not share its runtime.

You give, you receive

Every swap intent is one sentence with two halves. The maker states both, signs the statement, and the taker answers it with inputs of their own. Because both halves are exact, outpoints and quantities rather than approximations, the resulting transaction needs no interpretation from anyone.

YOU GIVE

The maker's side

Exact outpoints carrying an exact quantity of one asset, plus the maximum fee the maker will contribute, where the maker receives, and an expiry height after the signed checkpoint.

YOU RECEIVE

What the maker requires

Exact criteria: an asset type, a specific asset id or inscription id, and a minimum quantity, paid to the maker's receive script by the one transaction that settles the trade.

An intent carries a maker identity proof (BIP-322 over the intent digest, checked before publication), its visibility, a nonce, the protocol adapter versions, an optional taker binding, and the digest: SHA-256 over the sorted-key JSON of everything except the identity proof and the digest itself.

Two-stage signing

  1. The maker signs an intent.What they give (exact outpoints), what they require, where they receive, their fee budget, and an expiry. Nothing is pre-signed against a transaction that does not exist yet.
  2. The taker selects exact inputs.When a taker picks the assets they will hand over, the gateway builds one deterministic acceptance plan: a single transaction spending the maker's committed outpoints and the taker's selected outpoints.
  3. Each side signs its own inputs.Each participant signs only their own inputs with their own wallet. The maker's assets and the taker's assets each travel through an explicit transition to the output that receives their input's first sat.
  4. Everyone checks, then you send.The transaction is relayed only after every required signature exists, the complete transaction passes node preflight, and a user takes the explicit broadcast action.

The maker never signs a transaction before the taker's inputs exist. Non-interactive sighash constructions may arrive later, but only through new conformance vectors that prove the maker's assets, requested consideration, destination, and fee cannot change. Until then, this interactive two-party flow is the only path.

A stall is possible. Asset loss is not.

Every input commits to every output under SIGHASH_ALL. That closure has a precise consequence the verifier proves rather than promises: a transaction carrying only one party's signatures cannot be included in any block, because the other party's inputs are not signed.

Refusing the last signature stalls a swap. It cannot steal.

If a counterparty walks away at the final step, the trade does not happen and both sides keep exactly what they started with. Refusing that signature can stall the swap; it can never take the other party's asset. The verifier refuses any construction where a one-sided transaction could settle (ATOMICITY_IMPOSSIBLE is its name for this).

The same proof pass pins everything else: every maker-committed outpoint is spent exactly once, by the maker side; criteria are paid to the maker receive script at no less than the minimum; fee conservation holds and the maker share stays inside the budget; and no asset lands in the fee region, in unrelated change, or at the wrong party.

Private links and QR sharing

A private link is created client side, before the server learns anything: a random 256-bit key encrypts the intent with an authenticated cipher, only the ciphertext and routing metadata reach the server, and the key travels in the URL fragment, which browsers never send to a server.

Private intents are never listed, never logged in plaintext, and never exposed in events. The server cannot read the terms, and its logs never contain the fragment, the key, or a decrypted payload.

Lifecycle

A swap moves through named states, and every transition appends an event: DRAFT, LIVE, PRIVATE, MATCHING, AWAITING_MAKER_SIGNATURE, AWAITING_TAKER_SIGNATURE, READY_FOR_PREFLIGHT, READY_FOR_BROADCAST, MEMPOOL, CONFIRMED, EXPIRED, WITHDRAWN, CONFLICTED, INVALIDATED, REORGED.

A swap becomes unavailable immediately when a committed outpoint is spent, ownership changes, an authority goes stale, or the intent expires. A reorg appends an explicit reverted event naming the event it reverses, so a consumer never has to guess.

What can swap today

The settlement cohort ships for BTC to Ordinal, Ordinal to BTC, Ordinal to Ordinal, BTC to Rare Sat, Rare Sat to BTC, Rune to BTC, BTC to Rune, Rune to Rune, and Counterparty UTXO-attached assets through the heritage adapter.

A protocol joins this list only when an exact ownership resolver, transaction builder, signed-transaction verifier, settlement reconciler, and reorg handler all exist for it. A portfolio reader alone never qualifies a protocol, which is why the list grows slowly and never lies.

What the server sees

Ciphertext, not terms.

For a private swap the server holds ciphertext and routing metadata. It cannot read what you give, what you require, or where you receive. For a public swap the terms are public because you chose that, and the server still never signs, never holds funds, and never broadcasts without your action.

What your wallet signs is exactly the acceptance plan: your own inputs, and a signature that commits to every output in the single settling transaction. Adversarial cases, including changed recipients, output reordering, fee theft, hidden extra outputs, partial signatures, replayed intents, and ciphertext tampering, are covered in the vectors rather than hoped away.

Verify it yourself

  • Recompute the intent digest from its sorted-key JSON and compare it with the BIP-322 identity proof.
  • Run the reference verifier at verifier/swaps.js over any intent and acceptance plan.
  • Replay conformance/swap-vectors.json, including one party refusing the final signature.
  • Stream swap state changes through the realtime event envelope instead of polling.
